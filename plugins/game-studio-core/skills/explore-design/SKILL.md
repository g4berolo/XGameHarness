# /explore-design — 只想聊聊，先别写文件

## 这个 skill 的定位

harness 里其余 skill 都以「产出一份文档」为终点。但游戏设计里有大量时间花在
**「这个想法到底行不行」** 上 —— 此时产出文件是负担：写出来的东西下一轮就被推翻，
反而在 `design/gdd/` 里留下需要清理的垃圾。

本 skill 补的就是这一档：

| 阶段 | 用什么 |
|---|---|
| 还没有游戏，想点子 | `/brainstorm`（产出 `game-concept.md`）|
| **想改某个已有系统，但不知道怎么改** | **`/explore-design`（不产出任何文件）** |
| 已经决定要改什么，要写下来 | `/design-system` |
| 不知道该用哪个 skill | `/how-to-do` |

## 硬约束：不写任何文件

本 skill 的 frontmatter **不包含 `Write` / `Edit`** —— 这不是提醒，是机制。
即使用户中途说「顺手记一下」，也**不能**写，正确做法是转交 `/design-system`
或让用户自己记。

同样**不更新** `team/session-state/{identity}/active.md`。这是一次无痕探索。

**代价要如实告诉用户**：本次讨论的结论只存在于对话里，会话压缩(compaction)或
关闭后就没了。所以第 4 步的收束是必须的，不能聊完就散。

---

## 1. 确定探索对象

有参数 → 直接用。无参数 → 先读下面这些确定「现在有什么值得聊的」，
然后 `AskUserQuestion` 给 2-4 个候选方向：

- `plan/stage.md` —— frontmatter 的 `current_stage` + 当前阶段未完成的 Critical 行
- `design/gdd/systems-index.md` —— 状态为 In Design / 有 Open Questions 的系统
- 各 GDD 的 `## Open Questions` 段 —— 这里天然堆着「还没想清楚的事」
- `team/memo/{identity}/open/` —— 未处理的 memo

---

## 2. 先读，再说话

**在提出任何选项之前**把地基读完。这是本 skill 相对于随口聊天的唯一优势 ——
它带着项目的真实状态进场，而不是通用的游戏设计常识。

必读（存在才读，全部加守卫）：

- **目标系统的 GDD**：`design/gdd/[system].md` —— 现在是怎么设计的
- **上下游 GDD**：从 `systems-index.md` 拿依赖关系，读上下游 —— 改动会撞到谁
- **游戏支柱**：`design/gdd/game-pillars.md` —— 哪些路线一开始就违背支柱，直接排除
- **实际实现**：Grep/Glob 找对应代码 —— 文档说的和代码做的可能已经不一样

**遵守 R1（verify-before-label）**：GDD 头部的 Status 字段是意图快照(intent
snapshot)，不能只读 header 就下判断。说「这个系统已经设计完了」之前，要读 body
确认 section 里不是 `[To be designed]` 占位。

读完给一句话现状回述，让用户确认你理解的起点没错：

> **现状**：[system] 当前是 [一句话]。它被 [X] 依赖、依赖 [Y]。
> 代码侧 [已实现 / 还没有 / 与文档不一致的地方]。
> 你想动的是 [复述用户的意图]，对吗？

---

## 3. 摆选项，不替用户做决定

给 **2-4 条**可选路线。少于 2 条不叫探索（那是在推销一个方案），多于 4 条用户
选不动。

每条路线必须包含：

- **一句话概括** —— 这条路线的本质是什么
- **改动面** —— 会动到哪些系统、哪些文件、大概量级（XS / S / M / L）
- **代价** —— 放弃了什么、引入了什么新问题。**没有代价的选项说明你没想清楚**
- **对支柱的影响** —— 强化了哪条、牺牲了哪条
- **可逆性** —— 做错了能不能撤，撤的成本多大

再加一条几乎总是存在、但容易被忽略的路线：

- **什么都不做** —— 说清楚不做的后果。很多时候这是对的答案，尤其在项目早期，
  用户描述的「问题」还没有被试玩数据证实过

如果几条路线的差别本质上是猜测玩家反应，**直接说出来**，并指出这类分歧靠讨论
不可能收敛，应该走 `/prototype` + `/playtest-report` 去测，而不是继续在
`/explore-design` 里推演。

**可以 spawn subagent 拿专业输入**（遵守 R4，spawn 前把提示模板给用户确认）：

| 探索的东西 | spawn |
|---|---|
| 核心循环 / 系统拆解层面拿不准 | `game-studio-core:game-designer` |
| 公式、曲线、交互矩阵的可行性 | `game-studio-core:systems-designer` |
| 经济 / 掉落 / sink-faucet | `game-studio-core:economy-designer` |
| 改动的技术代价 | `game-studio-core:technical-director` |
| UE 侧能不能做、代价多大 | `unreal-pack:unreal-specialist` |

subagent 的产出是**给用户看的分析**，不落文件（agent 侧也不许写）。
插件前缀是必须的 —— 裸名会被拒（`Agent type not found`）。

---

## 4. 收束（不能省）

用 `AskUserQuestion` 让用户落一个决定：

- 「聊到这里，下一步？」
  - **「选 [路线 N]，去 `/design-system` 写下来」** —— 用 Skill tool 直接调起
    `/design-system [system-name]`，并把本次探索的结论（选定路线、排除掉的路线
    及理由、明确的非目标）作为上下文带过去
  - **「选 [路线 N]，但先做原型验证」** —— 调起 `/prototype`
  - **「都不选，问题还没想清楚」** —— 明确说下次继续时需要什么新信息
    （试玩数据？某个前置系统先定下来？）
  - **「什么都不做」** —— 这是有效结论，不要引导用户避开它

**转交时必须说明**：本次讨论没有留下任何文件，结论只随这次交接传递。如果用户
选了「都不选」但想保留思路，告诉他两个选项：自己记，或者调 `/design-system`
只写 Lite 层（意图 + 非目标），把结论固化成一份 30 行的文档。

---

## 原则

- **不写文件** —— 见上文硬约束
- **不替用户收敛** —— 可以给推荐（并说明理由），但不能只给一个选项
- **不空谈** —— 每条路线都要落到具体的系统名、文件、量级，说不出改动面的路线
  说明还没读够，回第 2 步
- **诚实标注不确定性** —— 分不清「设计问题」和「需要试玩验证的问题」是这个
  阶段最常见的浪费；分不清就说分不清

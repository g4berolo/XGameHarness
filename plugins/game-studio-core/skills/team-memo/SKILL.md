# 团队便条

Claude 和 Codex 在 XGS 中使用宿主提供的 `xgs_memo`。工具按当前会话的项目和登录人执行。涉及多人候选方案的公开评审使用 proposal-review。

- **起草**：给便条写一个可辨识的标题。读本说明要对方做什么、为什么；将可验证的完成条件列成清单。只要求看看措辞时，展示草稿并等待发送指示。
- **发送**：用户说“给某人发一条”时，用工具核对项目成员并发送。昵称有歧义才询问。向用户回报服务器确认的收件人、标题和便条编号。回执只能证明服务器已收件，不能推断对方已读。
- **操作编号**：先用 `list` 读取当前项目成员和收发记录；发送用 `send`。写操作生成一个 UUID 作为 `operationId`，重试原操作沿用该编号。两条内容相同但独立的便条使用不同编号。
- **查收和处理**：用工具查看当前收发的便条，定位原编号后用 `reply` 回复或用 `check` 更新勾选项。同名便条按收发人和编号区分。用户要求完成时，由收件人用 `close`提交，只有收到成功回执才报告归档完成。
- **断线和重试**：回执为 `queued: true`（待发送）或 `memo.status: pending_archive`（待归档）时，如实说明当前状态，沿用原事项重试。同一请求等待回执时避免再新建一条。遇到未认证、无权限、工具缺失或服务版本不支持时，保留草稿并说明原因。不要为绕开失败去写项目文件、推 Git、用浏览器模拟操作，或要求用户手动提交。
- **历史兼容**：已有文件便条按[团队便条协议](../../docs/team-memo-protocol.md)读取。在独立 Harness 的文件工作流中，只有用户明确选择 Git 传递时才按文件协议处理；“已写入本机”“已提交”“已推送”分别报告。

起草或交付设计文档时，先按[设计交付与任务关联](../../docs/design-delivery.md)确认“评审草案 / 直接正式”的去向，沿用已明确的选择，并把实际原文、读本和候选版本关联回原任务。后续示例路径服从该选择；草案不写入正式 GDD/读本或正式系统索引。


# 候选方案起草

参数：主题，分类 gdd / systems / sprint。

需要把讨论整理后提交 XGS、汇总评论或修订已有候选时，在当前任务中读取并执行 [proposal-review](../proposal-review/SKILL.md)，不要要求用户另行调用技能。起草是准备步骤；用户已要求新增评审或选择修订旧案时，必须继续用 XGS 原生工具完成提交与核验，不能停在本地文件。

运行时适配：读取本插件 `docs/codex-runtime.md`。Codex 用 `$proposal-draft` 或读取本文件，Claude 使用插件技能入口；相对路径从本文件向上两级为插件根。

1. 读取现有正式设计、相关决策及当前Sprint，核对设计前提。区分已定事实、建议和待决定事项。
2. 与用户讨论2–4种方案及取舍，收敛到待讨论候选；不能把讨论中的偏好写成团队已批准决定。
3. 依照 `rules/design-docs.md` 和 write-digest 技能的读本规则，写出便于其他专业同事阅读的完整说明：目的、运行方式、取舍、例子及需要讨论的问题。不要只是技术原文摘要；具体数值只以原文为准。
4. 技术原文遵守 design-system 的结构；Sprint遵守 sprint-plan 和 `docs/task-execution.md`，分离[AI]与[HUMAN]任务及验收，保留独立人工审核。
5. 按已选择的去向保存原文和读本。直接正式的 GDD/系统按 design-system 写原文与读本并更新任务资料；Sprint 则按任务执行规则交给 sprint-plan 写入所选正式计划或看板，不生成 GDD。不执行下面的候选提交步骤；选择草案时继续。开发者不需要查看或编写 JSON。
6. 用户要求新增评审或选择修订旧案时，按 proposal-review 技能调用 XGS 原生 xgs_review 工具。新建使用 submit；修订先 get 当前候选，保留 id 并携带最新 revision/version 调用 revise，再 get 同一 id 核对已保存的读本、原文和版本。用户已选择修订旧案即已授权该次候选修订，不重复询问是否提交，不创建同名新案替代。
7. 汇总讨论时引用候选版本和意见作者，保留分歧，不虚构评论、身份或批准。新版本不能把旧版意见当作新版认可。
8. 只有候选负责人或已绑定任务的指定审批人在XGS预览正式文档并明确采纳后，才转换正式文档并归档候选。AI不得直接编辑 `team/reviews/`、伪造采纳记录或修改正式GDD来绕过此流程。

本地草稿即使同步到其他机器，也不代表已进入评审或已获认可。以原生工具确认的候选编号和版本为提交证据。

新增和修订都不得要求开发者导入文件、上传 JSON、复制粘贴正文到评审台或手动点击发布来完成 AI 已承接的提交。不得以“刷新即可看到”掩盖未提交。若工具缺失、无权限、候选已关闭或请求失败，明确说明尚未提交及具体阻碍，保留 Markdown；不能把手动导入作为替代流程，也不能绕过权限写 team/reviews/。仅要求起草或讨论时不擅自发布。

# 整理并提交评审

输入：讨论内容、草稿路径或候选编号；可补充分类和本次动作。

运行时适配：按需读取 [Codex 运行约定](../../docs/codex-runtime.md)。本文件向上两级为插件根。Claude 使用插件技能入口，Codex 使用 `$proposal-review`；XGS 中可选择本技能或直接请求使用它。使用 XGS 提供的原生 `xgs_review` 工具（宿主可能显示 MCP 前缀），不使用 Computer Use 提交评审。

## 1. 确定要整理的内容

- 区分起草、提交新候选、汇总评论、修订已有候选。仅整理不代表授权发布，提交候选不代表采纳正式文档。
- 确认当前项目和分类 `gdd` / `systems` / `sprint`。读取相关正式设计、决策、Sprint 和用户指定材料，不扫描整个项目来凑上下文。索引缺失时查找实际文档，不自行补造索引。
- 汇总现有评审时，先读取指定候选最新内容、版本、状态和完整评论。项目同步的 `team/reviews/<id>.json` 只读；不能确认是否最新时说明快照时间和限制。读不到评论就索取候选或导出内容，不推测讨论结果。
- 起草全新方案时可依照 [proposal-draft](../proposal-draft/SKILL.md) 组织候选，但不强制已有方案重新脑暴。拆开独立议题，避免把整场聊天堆成一个候选。

## 2. 写成跨专业能读懂的方案

动笔前读取 [设计文档规则](../../rules/design-docs.md) 的“读本怎么写”，以及 [write-digest](../write-digest/SKILL.md) 的完整性、理解性、简洁判据。这些规则是唯一维护源，不另创一套较松的评审文风。

- `reader` 是完整读本，`source` 是精确原文。读本不能只是摘要或“详见原文”。先完整阅读原文，再写机制、条件、例外、交互例子及对接影响；不要从截取片段生成完整结论。
- GDD/系统按原文档位使用 Full 九节或 Lite 五节，三级标题连续编号。机制构成必须有图；讲空间、朝向和连接的部分使用 SVG 图解。图遵守插件 `docs/diagrams.md`，使用主题词表和代码围栏，不用裸 HTML 或 `<br>` 排版。
- 遵守短句、主动语态、一段一事、不重复、不打比方等句子规则。正文用白话，标识符只进名词对照。具体设计数值和公式只放原文，不能在读本复制一套易过期数值。
- 未批准的方案明确写为建议。取舍必须在原文有依据；尚未确定的假设和问题标成待讨论，不编造成既定事实。评审问题单独放在提交说明里，不破坏读本固定节名；Full 也可在“对接”末尾列未定事项。
- Sprint 使用同样的完整、易懂、简洁要求，按目标、工作顺序、依赖、交付和验收组织读本，不硬套系统机制章节。原文遵守 [任务执行规则](../../docs/task-execution.md)，最小任务分开 `[AI]` 制作与 `[HUMAN]` 审核，不因候选发布就标为完成。

## 3. 整理评论与修订

先给一段白话说明目前的共同点、分歧和待决定事项，再用表格列“议题、意见来源及版本、建议处理、影响”。作者、评论编号和版本属于追溯信息，放在表格中，不混入设计读本正文。

区分明确同意、提出疑问、建议修改和未回应。重复意见可合并展示但保留全部来源；不以评论数或沉默推断通过，不把旧版认可转移到新版。建议处理写“建议采纳/待澄清/建议不纳入”，不能冒充负责人已采纳。

修订时保留原候选编号，列出相对当前版的变化，更新读本和原文，附逐条回应。非负责人只能准备建议或发表评论，不能以创建同名候选绕过负责人限制。已归档候选只读；需要后续变更时另起候选并注明来源。

## 4. 提交到 XGS

按 [提交与核验](references/submission.md) 执行。AI 承接的新增和修订必须直接调用原生工具；评审台的直接编写和导入入口只供用户自发手工操作，不是 AI 的交付步骤。

用户已明确要求提交且目标、内容明确时，直接调用原生 `xgs_review`，不重复索要同一授权。工具固定绑定当前对话的项目和身份，复用服务器权限与单写者；不要读取令牌或调用私有接口。

使用 `list` 查候选摘要，`get` 取读本、原文与完整评论，`submit` 新建，`revise` 修改自己的候选，`comment` 发表当前用户的意见。变更提供稳定的 `operationId`；修订附最新 `revision` 和 `version`。重试复用编号，结果不明先 `get`/`list` 核对，不盲目换编号重发。

用户选择“修订旧案”已授权更新该候选，不要只修改本地草稿后要求再次导入。先 get 确认目标和最新状态，revise 保留同一 id；新增 submit 后使用返回的 id。两者都须再 get 核对保存后的标题、读本、原文及版本，成功后报告候选编号与版本。核对不一致则报告未确认并继续定位，不能声称已同步；不要求用户上传 JSON、粘贴正文或手动发布来补完流程。

可以传 `readerFile`/`sourceFile` 指向项目里的 Markdown，不必在聊天重贴全文。内嵌图使用 `svg` 围栏；archify 的独立 HTML 可通过 `diagrams` 提供项目相对路径和图注，工具将完整图内容随候选保存，其他设备无需原机器的本地路径。HTML 在阅读器隔离预览，脚本不运行；不要承诺原网页按钮、导出或动画都能工作。大图可拆分候选或使用 archify 的 SVG 交付。

JSON 只是内部协议，不能要求用户查看、编辑或手动上传 JSON，也不要把工具参数当作交付内容展示。工具未出现或服务器不支持时，说明需要更新 XGS/Harness、登录服务器模式并新开对话，保留已整理的 Markdown；不能退回 Computer Use 或把 JSON 导入当成完成。

最终只报告真实完成阶段。提交成功给出候选标题、分类、编号及评审台入口；未确认时明确未确认。汇总意见与正式采纳继续保持区别。

提交或修订后按[设计交付与任务关联](../../docs/design-delivery.md)把候选编号、绑定版本、原文和读本回写原任务；不能只返回一段成功消息。需要正式交付时绑定 requiresAdoption。

正式转换由候选负责人或已绑定任务的当前指定审批人在 XGS 预览目标、差异和读本后明确“采纳并归档”。本技能可准备正式目标与采纳说明，不替代这次人工决定，不提前覆盖 GDD、Sprint 或归档记录。


## 评论必须逐条处理

每条评论和回复默认“待定”。所有有项目访问权的成员都能处理，状态只有“通过已合并”“待定”“已取消”。保留评论内容、版本和真实处理人历史，不删除意见来消除待办。旧评论没有状态时也算待定。

使用 get 读取当前状态。只有用户明确要求处理具体评论时，才用 resolve（commentId、status、expectedStatus、operationId）。merged表示“通过已合并”，cancelled表示“已取消”，pending表示“待定”；不能仅因用户要求发布、采纳或撤回就批量消除待定。不得用“建议采纳”冒充已经合并。

采纳正式文档和提出者撤回草案均要求所有评论已处理。还有待定时列出具体问题，请开发者继续处理；服务器会拒绝绕过。撤回由提出者在XGS操作，保留候选和评论历史，不能当作删除；工具不开放withdraw或adopt。已撤回和已采纳候选只读。

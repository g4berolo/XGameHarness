# 设计起草、关联资料与正式交付

用于起草系统方案、GDD、读本及其看板任务。任务身份与服务器写入规则见 [任务执行](task-execution.md)。本规则同时供 Claude 与 Codex 使用。

## 写入前确认去向

起草人只说“起草系统方案 / 写 GDD”且未指定去向时，先问一次：“这次先写评审草案，还是直接写正式 GDD 和读本？”等待回答后再创建目标文件。已明确选择、或继续同一次起草时沿用原选择，不重复询问。读取背景、梳理依赖可以先进行。仅要求讨论时不擅自写入或发布。

- **评审草案**：原文、读本放在 `design/proposals/<任务编号或主题>/gdd/<文件名>.md` 与同目录 `digest/<文件名>.md`；有既存草稿路径则保留。提交和修订走 proposal-review；提交成功仍是候选，不能更新正式系统索引为已批准。
- **直接正式**：直接编辑 `design/gdd/<文件名>.md` 与 `design/digest/<同名文件>.md`，保留已有文件、约束和人工修改。不为新文档另造评审候选。路径的“正式”表示文档位置，不代表已经通过人工验收、进入 Git 或同步到同事机器；记录真实的 Designed / 待验收状态。遵守项目现有发布方式和本次提交推送授权。
- **已有候选**：若本任务已绑定开放候选，转正仍走原候选采纳；不能改写正式文件、撤掉关联或另建同名卡来绕过旧意见和审批。未确定是新稿还是已有候选时先读取任务和候选再确认。

确定本次 `designMode`（candidate / formal）、`sourcePath`、`readerPath` 和关联任务编号；在个人 active.md 中保留它们供恢复时使用。后续技能中的原文路径、读本路径、session-state 和输出链接都使用这次选定的路径。草案模式不写正式系统索引；正式模式索引指向实际文件，AI design-review 的通过不能冒充审批人验收。

## 每次交付更新原任务的关联资料

用户给了任务编号时，用 `xgs_project_board get` 定位原卡，核对真实 UUID、标题与交付目标、经办人、审批人、任务修订和现有资料。用户主题与该编号的任务目标不符时先确认，不自动换卡或覆盖任务内容。未指定任务时只在已有上下文中定位；有歧义询问，不擅自建卡或把同标题认成同一任务。

1. 核对实际原文、读本、前提说明和任务说明文件。使用可点击的项目相对链接，例如 `[时间与四季原文](/design/proposals/S2-006/gdd/时间与四季.md)`。记录实际版本或哈希。不要按标题猜路径，不把本机绝对路径当作全员可用资料。
2. 若已提交或修订候选，先 `xgs_review get` 回读 id、最新 version 与内容。将 `reviewId`、`reviewVersion` 和本次要补充的 `gdd` 主文档链接合并为一次 `task.update.payload.patch`，由候选负责人携带当前任务修订提交。仅候选转正路线且交付要求正式采用时设 `requiresAdoption: true`；直接正式路线不创建候选、不设置这道门禁。没有候选的起草阶段只更新实际资料链接。仅在证据文字中写“已提交”不能替代绑定。
3. 回读任务，确认资料和绑定版本已保存，再使用最新 `taskRevision` 调用 `task.addEvidence`，附全部资料路径（每行一条）、交付说明及实际 `targetArtifactRevision`，由此进入待验收。来源未同步、文件缺失或仅在起草机时写明；上传候选正文不等于文件已进入项目仓。
4. 候选每次修订后重走上述顺序，更新绑定版后再提交本版证据。交付字段更新会使旧证据过期，不能先提交证据再改关联。只报告服务器已确认的步骤；候选提交成功但关联失败时，明确“候选已提交，任务关联未完成”，保留原编号重试，不另建候选。

旧宿主没有这些字段时，不发送未知参数，也不假装关联成功。保留路径和候选回执，说明需升级服务/客户端。没有 XGS 的文件型项目，把相同资料链接、版本和验收人写回原任务表，不能编造服务器回执。

## 审批、转正与任务完成

指定任务审批人可以不同于起草人。起草人建立候选关联后，服务端根据原任务的当前审批人授权采纳绑定版；普通成员没有因为“看得到候选”就获得采纳权限。修改候选和撤回仍由候选负责人处理。已有候选关联的任务改派审批人也会转移采纳权，须由起草人调整；其他任务仍沿用原来的人员编辑规则。不要改派成自己以绕过权限。

候选转正路线中，审批人核对绑定版、读本、原文及全部评论。要求正式采用的任务，先在 XGS 关联候选预览正式目标、原文和读本差异，明确采纳并归档。服务器核对正式文件哈希并确认 Git 发布后才算转正。仅已提交、本地稿、待推送、已撤回、旧版采纳或“意见都处理了”都不等于当前版已正式采用。

回读任务的只读 `review` 和候选实际采纳回执，确认正式路径、采用版本、提交号，再由当前指定审批人 `task.confirm`，填写实际验收结论和目标版本。两步不是跨 Git/数据库的原子操作：文档发布成功但任务确认失败时，报告“正式文档已发布，任务仍待验收”，核对后补做原任务确认，不重复采纳。

原生评审工具目前没有 preview/adopt 时，从任务关联进入评审台完成明确采纳；不能编造工具能力或私调服务接口。只要求评审候选而不要求正式交付的任务，按已约定验收条件执行，不能自行加上强制发布要求。
